# Key decisions

1. **Modular monolith: one FastAPI app plus a separate scheduler process, bot webhook mounted in FastAPI.** Reason: at ≤100 users, extra deploy units cost more than they give. The scheduler stays separate so jobs never double-run.
2. **FastAPI serves the built SPA from the same origin.** Reason: no CORS, no cross-site cookie problems in Telegram webviews, and one fewer Railway service.
3. **Telegram initData validated server-side, then a 24h JWT held in memory (no cookies).** Reason: cookies are unreliable in Telegram webviews, and re-validating initData on every launch is cheap.
4. **Gold wallet per (user, partnership); XP and levels global per user.** Reason: Gold from an ended partnership can't be spent with a new companion, and permanent progression stays with the user.
5. **Ledger is the source of truth; cached balance updated in the same transaction (CHECK ≥ 0, row locks, unique idempotency keys).** Reason: atomic, idempotent Gold and XP, with cheap balance reads.
6. **Recurring quest = template + accepted revision + one occurrence per local date (unique constraint).** Reason: generation is idempotent and catches up after restarts, and terms changes apply only to future occurrences through revisions.
7. **Transactional notification outbox in Postgres; no Redis.** Reason: messages are sent only after commit and survive restarts, with one fewer piece of infrastructure.
8. **Files on a Railway volume behind a `StorageBackend` interface, served through an authorized endpoint.** Reason: the client chose it for simplicity; S3 can be swapped in later without route changes.
9. **pnpm (frontend + root scripts) and uv (backend); TS types generated from OpenAPI.** Reason: fast installs and one set of commands (`pnpm test`, `pnpm lint`, `pnpm e2e`), with no hand-copied API types.
10. **Playwright authenticates with genuinely signed initData and a Telegram WebApp stub.** Reason: E2E tests exercise the real auth path without real Telegram.
11. **All database sessions run at READ COMMITTED, pinned explicitly on every engine (`app/db/session.py::ISOLATION_LEVEL`).** Reason: the `partnership_one_active_per_user` trigger takes per-user advisory locks and then checks for another active partnership; that check only sees a concurrent transaction's freshly committed row because each statement under READ COMMITTED takes a new snapshot. Under REPEATABLE READ or SERIALIZABLE the snapshot is fixed at the first statement, so two racing inserts could both pass (or fail with serialization errors the services do not retry). The same holds for the row-lock (`SELECT ... FOR UPDATE`) wallet debit pattern. Raising the isolation level later requires revisiting the trigger and those services first.
12. **i18n uses namespaced files `frontend/src/i18n/{en,uk}/<ns>.json` (glob-loaded, key-parity tested).** Reason: smaller per-feature files and fewer merge conflicts. This supersedes ARCHITECTURE.md:109 and :328, which say `i18n/{en,uk}.json`.
13. **Account deletion keeps a scrubbed `user` row and frees the Telegram id: `tg_user_id` becomes `-id`, `deleted_at` is set.** Reason: ledger, quest and purchase rows (and the companion's history) reference the user, so the row stays, but the Telegram link is PII. Telegram ids are validated as positive, so `-id` is unique and can never match a real login. Effects: every JWT already issued is rejected (`current_user` refuses deleted users); logging in again with the same Telegram account creates a new, empty account with no link to the old one. The frontend ends the session after a deletion so it does not silently re-register; the AuthGate retry does that only on purpose.
14. **Pairing details (S06).** Invite tokens are 32 random bytes (`token_urlsafe`), stored as sha256 only, and the server never takes them from a URL: they travel only in JSON bodies (`POST /partnership/invitations/preview` was added so the accept screen can show the inviter without a token in an API URL). The client does carry the token in a URL (Telegram's `startapp=invite_<token>` and the SPA route `/invite/:token`), so the page sends no Referer (`<meta name="referrer" content="no-referrer">` in index.html plus a `Referrer-Policy: no-referrer` header on SPA responses). Accepting requires a finished onboarding; a new user who opens an invite link onboards first and is returned to the invitation. Typed confirmations are the fixed words `LEAVE` and `DELETE` in every locale. Re-pairing reactivates the old partnership row and its wallets and restores only the rewards that ending the partnership hid (flagged `reward.hidden_by_partnership_end`, migration 0002) back to active (or sold_out when none remain) and clears the flag; rewards their creator had hidden before the leave stay hidden. An explicit flag rather than matching `updated_at == ended_at`, which any later edit of a hidden reward would break; cancelled quests stay cancelled. Lock order is always user rows by ascending id, then the invitation/partnership row.
15. **Quest offer flow (S07).** Every quest is a template with revision 1 (its offered terms; `current_revision_id` points at it from creation, `pending` until the offer is accepted or declined). A one-time quest also gets its single occurrence at creation (`offered`); a recurring one gets its first occurrence only when accepted, through `quests/occurrences.ensure_occurrence`. Because a recurring offer has no occurrence, quests are addressable both as `/quests/{occurrence_id}` and `/quest-templates/{template_id}` (GET, PATCH, accept, decline, cancel), with the same service code; this adds `GET /quest-templates` and the template routes to ARCHITECTURE §5. Accept and decline act on the offer while the template is `offered`, otherwise on the pending revision (one per template, partial unique index, migration 0003); a newer proposal supersedes the pending one. An accepted revision changes the template and future occurrences only; existing `terms_snapshot` values stay, except for a one-time quest whose single occurrence is still `active` (it has no future occurrence, so it takes the new terms). Cancelling an occurrence of a recurring quest cancels only that occurrence; cancelling the template cancels it and its offered/active occurrences (in_review ones are left to review). Non-members get 404, the wrong member 403, a forbidden state 409, an ended partnership 409 (detail stays readable as history). Decline reasons live on the row (`quest_occurrence.decline_reason`, new `quest_revision.decline_reason`), are scrubbed on account deletion and never copied into journal/notification payloads. Lock order: partnership `FOR SHARE`, then template, occurrence, revision `FOR UPDATE` (create locks the creator's user row first), so `leave` and account deletion (`FOR UPDATE` on the partnership) serialize with quest writes. *Addition to ARCHITECTURE §5 (for S09/S13):* the template routes are `GET /quest-templates` (list; `?role=player|gm&status=…&recurrence=…`), `GET /quest-templates/{template_id}` (detail with `latest_occurrence`), `PATCH /quest-templates/{template_id}`, and `POST /quest-templates/{template_id}/accept`, `/decline` (body `{reason?}`) and `/cancel`; they mirror `/quests/{occurrence_id}` and return `TemplateDetail`. *Closed quests (review fix-up):* a pending revision can be accepted or declined only while the template is active/paused and, for a one-time quest, its occurrence is active (409 otherwise); cancelling a template and `end_partnership` supersede its pending revisions, and reads never show a pending revision on a closed template. A one-time offer whose deadline has passed cannot be accepted (409; it can still be declined or cancelled). Revision decline reasons are returned to both members in `RevisionOut.decline_reason`, and `TemplateOut.last_declined_revision` is the newest declined revision (a declined offer, or a declined proposal not yet replaced by a newer accepted revision).
16. **Quest completion and the economy (S08).** `quests/completion.complete_occurrence` is the only payout path; `confirm` (creator) and the auto-confirm branch of `submit` (assignee) both call it. One transaction: occurrence `in_review -> completed` (a one-time template `active -> completed`), submission approved, `economy.service.post` credits the assignee's `(user, partnership)` wallet (upserted, `FOR UPDATE`) with ledger key `quest:{occurrence_id}`, `progression.service.award_quest_xp` writes the occurrence's single `xp_transaction` and adds the same XP to `character.total_xp` and the quest attribute, a daily template's streak moves, and journal events (`quest_completed`, `level_up`, `attribute_level_up`) plus one notification are written. Gold and XP come only from `terms_snapshot`. A payout needs an active partnership and two non-deleted members (409 otherwise). Exactly once: occurrence row lock + state machine, then the unique ledger key and unique `xp_transaction.quest_occurrence_id` (a duplicate aborts the transaction). Submit is refused after `due_at` (409); an in-review quest can still be confirmed after it. **Lock order** (all writers): `idempotency_key` claim (when a key is sent) -> partnership `FOR SHARE` -> template -> occurrence -> revision / submission -> wallet -> character -> character_attribute -> quest_streak; `leave`/account deletion lock the two user rows (ascending id) `FOR NO KEY UPDATE`, then the partnership `FOR UPDATE`, so they serialize with payouts on the partnership row. User rows are never locked plain `FOR UPDATE` (`partnerships.lock_users`, `users.service.lock_user`, onboarding): a payout that already holds the partnership `FOR SHARE` inserts rows with an FK to `user` (ledger, XP, journal, notification, submission, idempotency key), and each FK check takes `FOR KEY SHARE` on the user row; a full `FOR UPDATE` there made leave/deletion (waiting for the partnership) and the payout (waiting for the user row) deadlock (40P01). For the same reason no transaction updates a user key column: `user.tg_user_id` is unique only through the partial index `ux_user_tg_user_id_live` (`WHERE tg_user_id > 0`, migration 0005, plus a plain lookup index) instead of a unique constraint, because Postgres counts only non-partial unique indexes as keys, so deletion's `tg_user_id = -id` rewrite is a no-key update and does not wait for a concurrent FK check (e.g. the deleting user's own Idempotency-Key claim). Login upserts with `ON CONFLICT (tg_user_id) WHERE tg_user_id > 0`. Forced-interleaving tests in `test_concurrency.py` pin this. **Idempotency-Key** (`core/idempotency.py`, on `/submit` and `/confirm`): 1-128 visible ASCII chars; the `(user_id, key)` row is claimed with `INSERT ... ON CONFLICT DO NOTHING` inside the command's transaction and receives the response before commit, so the effect and the stored response commit together; a parallel request with the same key blocks on that insert and then replays (header `Idempotent-Replayed: true`); errors are not cached (the claim rolls back); reuse with another endpoint or body is 422; rows expire after 24h: a row older than the TTL is never replayed (the next claim locks and takes it over), even if the purge job never runs. A stored response is the quest detail, which carries both members' comments, so account deletion deletes the idempotency rows of the deleted user and of every companion they ever had. Header keys never become ledger keys directly: purchases must use `economy.service.purchase_key(user_id, key)` = `purchase:{user_id}:{key}` (<= 255 chars). **Schema (0004):** CHECK `ck_gold_transaction_reference_matches_type` (quest_reward needs `quest_occurrence_id`, purchase/refund need `purchase_id`), composite FK `gold_transaction(wallet_id, user_id, partnership_id) -> wallet(id, user_id, partnership_id)`, indexes on `gold_transaction(wallet_id)`, `(user_id, id)`, `xp_transaction(user_id)`, `idempotency_key(created_at)`. **Revisions:** submitting a one-time quest supersedes its pending revision (the player submitted against the accepted terms; after a redo the GM can propose again); completing a one-time quest supersedes any left. Recurring offers keep no offer deadline: accepting creates the current period's occurrence with its own `due_at`, so a late acceptance never revives a past period. **Economy API:** `GET /economy/balance` -> `{active, frozen[]}`; `GET /economy/transactions?cursor=&limit=` -> my rows only (`user_id`), newest first, opaque keyset cursor, no idempotency keys exposed. When submitting a one-time quest supersedes the GM's pending revision, a `quest_revision_superseded` journal event (by the player) and a notification to the GM are written (ids and terms only). A submission attachment must be the assignee's own `quest_photo` uploaded for the quest's partnership (`file.partnership_id`). Submit/confirm/request-redo return `QuestActionResult` (the occurrence detail plus `completion` when this request paid out).
17. **Reward shop and inventory (S10).** `rewards/service.py` (create, PATCH, list, purchase) and `inventory/service.py` (request, schedule, fulfil, dispute, refund); voucher transitions go only through `rewards/state.py`, a `(status, action, actor)` table: purchased -request(buyer)-> requested -schedule(provider)-> scheduled (re-scheduling allowed) -fulfill(provider)-> fulfilled -dispute(buyer, <= 48h after `fulfilled_at`)-> requested (schedule and fulfilment cleared, no Gold change); refund: provider from purchased/requested/scheduled, buyer only from purchased. An actor that may never do an action gets 403, a wrong status 409. `cancelled` is reserved (nothing enters it). **Money:** a purchase debits through `economy.service.post` with `purchase_key(buyer_id, Idempotency-Key)` (the header is required on `/purchase`; the claim/replay of DECISIONS #16 applies, a key reused after the 24h window is 409 because the purchase row keeps the ledger key); a refund credits the buyer's wallet of the purchase's partnership with `refund:{purchase_id}`, also when that partnership has ended (frozen wallet). Price and terms come from the reward under lock and are snapshotted on the purchase (`reward_snapshot`, `price_paid`); PATCH never touches purchases. **Quantity:** `quantity_remaining` counts down per purchase (`sold_out` at 0) and a refund gives one unit back (sold_out -> active; a hidden reward stays hidden). A PATCHed `quantity_limit` sets `remaining = max(0, limit - live purchases)` (live = not refunded/cancelled); null makes it unlimited. Cooldown: the buyer's latest live purchase of that reward must be at least `cooldown_days` old. **Writes need an active partnership** (create, PATCH, purchase, request/schedule/fulfil/dispute; 409 otherwise); only a refund works after the partnership ended. So a creator can never edit a reward while `hidden_by_partnership_end` is set, which settles the S06 question: the flag is cleared by re-pairing, and PATCH also clears it (never set on an active partnership anyway); it is in no request or response schema. A reward from `wishlist_item_id` needs an open, unlinked item of the active companion (422 otherwise, 409 if already offered/archived); the item becomes `offered` with `linked_reward_id`. **Lock order:** idempotency claim -> (create only) creator's user row `FOR NO KEY UPDATE` -> partnership `FOR SHARE` -> wishlist item / reward `FOR UPDATE` -> purchase `FOR UPDATE` -> wallet `FOR UPDATE`; leave/deletion lock user rows then the partnership `FOR UPDATE`, so they serialize on the partnership; forced-interleaving tests (`test_purchase_concurrency.py`) pin purchase vs leave (either member), purchase vs deletion (either member), refund vs deletion, and leave-first (purchase refused, no effect). **Schema (0006):** composite FK `reward_purchase(reward_id, partnership_id) -> reward(id, partnership_id)`, indexes `reward(partnership_id, creator_id)`, `reward_purchase(reward_id, buyer_id)`, `(buyer_id, id)`, `(provider_id, id)`. Every purchase and transition writes a shared journal event and a `rewards` notification to the other member (`reward_created` for visible new rewards, `reward_purchased|requested|scheduled|fulfilled|disputed|refunded`); payloads hold ids, title, price (and `scheduled_for`), never the schedule note. Deletion already scrubs `schedule_note` (provider) and both members' idempotency rows.
